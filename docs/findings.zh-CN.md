# 发现记录（持续更新）

本文件累计记录 TrainingFreeSAM3D 在实验中**已经确认、可以写进论文**的结论。
与 `docs/stream_merge_v2.zh-CN.md` 的区别：那份是给人看的设计与结果说明，本文件只留
"发现了什么 + 证据 + 出处"，按阶段追加，写作时直接取用。

**更新规则**

1. 每完成一个阶段（0a / 0b / 0c / 第 1 阶段 / 第 2 阶段 …）追加一节，不删除旧结论。
2. 新证据推翻旧结论时，**就地标注"修正"**，写清新旧数值和原因，不静默改写。
3. 每条结论后面必须给出口径（数据集、指标、是否段平滑、是否用 GT），否则不进本文件。
4. 用 GT 得到的数字一律标注"（上限）"，不能当作方法结果引用。

**统一口径**（除非另注）

- 数据集：ScanNet 16 个验证场景，809 帧；每帧点云 = ESAM 约定的 20k 采样点。
- 输入分割：冻结的 FastSAM-x，逐帧原始 mask 经互斥分组得到"碎片"。
- 评估：ESAM 网格顶点协议，thing 类 GT（≥100 顶点），场景平均；AP50/AP25 为段平滑后
  （ESAM mesh-segment 平滑，阈值 0.5），平均最佳 IoU、召回@0.5 同口径。
- 参考：ESAM-E 官方输出在同一评估代码下为 **AP50 0.589 / AP25 0.722 / 平均最佳 IoU 0.691 /
  召回@0.5 0.726 / 40 mask 每场景**。

## 阶段 0a：GT-oracle 上限（不训练）

**问题**：把跨帧合并的打分换成 GT（该粘的一定粘），这条"碎片 + 体素关联"的路线天花板在哪？
它相对 ESAM 的跨帧合并规则和仓库里旧的记忆是否有优势？

**F0a.1　逐帧合并本身有很高的天花板，且高于 ESAM 的对应模块。**
逐帧口径（平均最佳 IoU，16 场景）：FastSAM 原始碎片 0.532 → GroupMergeNet 0.627 →
提议打分 0.688 → ESAM 只做合并的部分 0.702 → ESAM 完整版 0.754 → GT-oracle 合并 0.769。
结论：仅靠"把碎片粘起来"就有可能超过 ESAM 完整版，说明瓶颈不在合并判据是否够聪明。
出处：`esam_granularity`、`merge_net`、`mask_scorer` 三份文档；`docs/stream_merge_v2.zh-CN.md` §1。

**F0a.2　场景级：oracle 合并把覆盖率大幅拉高，但 AP50 一分未涨。**
窗口记忆用 GT 打分在线跑（win_w1）：平均最佳 IoU **0.768**、召回@0.5 **0.877**，
而现有默认管线（无 GT）分别是 0.458 / 0.498，ESAM-E 是 0.691 / 0.726。
但段平滑后 AP50 只有 **0.362**，与默认管线 0.365 几乎相同，远低于 ESAM 的 0.589。
即：覆盖率已全面反超 ESAM，AP50 却卡住。
出处：`work_dirs/stream_v2/phase0/summary.md`。

**F0a.3　每场景输出 mask 数是 ESAM 的近 3 倍（112 对 40）。**
oracle 合并下平均最佳 IoU 已经 0.768，召回 0.877，但每场景要输出 112 个 mask 才能拿到这些覆盖率，
其中大量是低质量输出。这就是 F0a.2 中"覆盖率涨、AP 不涨"的直接原因假设。
出处：同上。

**F0a.4　窗口长度在 oracle 打分下没有任何作用。**
win_w1 / win_w3 / win_w5（以及关掉"过去帧合并""物体间合并"的变体）逐位相同：
112 mask、AP50 0.362、AP25 0.426、IoU 0.768、召回 0.877 全部一致。
原因是结构性的：oracle 打分 = "两端纯度 ≥0.8 且多数 GT 相同"，"同 GT"是等价关系、合并传递，
因此不存在需要窗口事后纠正的错粘。**窗口改错的价值在 oracle 口径下不可测量**，留给第 2 阶段的学习打分器。
出处：同上。

**F0a.5　"GT 直接归类"（gt_assoc）并不比 oracle 窗口记忆更好。**
gt_assoc 平均最佳 IoU 0.781、召回 0.894，覆盖率略高于 win_w1（0.768 / 0.877），
但它多渲染了垃圾单例（119 对 112 mask），AP50 反而略低（0.353 对 0.362）。
两条互相独立的实现（GT 直接归类 vs 窗口图 + oracle + 聚类 + 编号）覆盖率互证一致，
作为 sanity check 通过。
出处：同上。

**F0a.6　（0b 阶段的修正）0a 文档中的"体素渲染硬上限 0.788"复现不出。**
重测结果为：网格 GT 直接走 5 cm 体素再渲染回网格，段平滑后 AP50 **1.000**（平均最佳 IoU 0.997）、
未平滑 0.999（0.926）；同机制换成真实观测点（逐帧 20k 点、全帧累计）段平滑后 **0.965**（0.891）、
未平滑 0.941（0.739）。仓库中找不到产生 0.788 的代码或结果文件，该数字不再引用。
出处：`work_dirs/stream_v2/phase0b/summary.md`。

**0a 的总结论（0b 修正后）**：合并决定覆盖率（平均最佳 IoU 0.458 → 0.768），
AP 卡在输出端的清理和排序，而不是卡在合并判据。

## 阶段 0b：输出端处理与 AP 上限（不训练）

**问题**：在"合并完美"之上补上输出端处理（排序 + 清理 + top-K），AP 的真正上限是多少？
不用 GT 的免费收尾能做到多少？

**F0b.1　垃圾 mask 的定义与构成：只在一帧里出现的"混合碎片"。**
段平滑后每场景 112 个 mask，按 AP50 贪心匹配归类为：正确 23.9、重复 3.4、部分重叠 9.2、
垃圾 75.4。垃圾的定义是"与任何 GT 的最佳 IoU < 0.25"。垃圾 mask 同时满足三条：
**90% 只被看到 1 帧、88% 由混了两个物体的碎片组成（纯度 <0.8 的点占一半以上）、72% 不到 500 顶点**；
墙 / 地面 / 天花板占比 **0%**。
本质：某一帧里切错的一块碎片自己单独开了一个物体，之后再也没被看到。
出处：`work_dirs/stream_v2/phase0b/summary.md` §1。

**F0b.2　收尾做好以后，上限很高。**
完美合并 + 完美排序 + 场景级 NMS（均用 GT，属上限）段平滑后 AP50 **0.877**，
远高于 ESAM-E 的 0.589（+0.288）。
同一评估代码下，"ESAM 自己的输出 + 完美排序"只有 **0.724**（40.2 mask/场景，dup_rate 0.090）。
即：**FastSAM 碎片 + 完美合并的底子比 ESAM 的实际输出好（合并用了 GT，不是方法结果）。**
出处：`work_dirs/stream_v2/phase0b/summary.md` §2、§3。

**F0b.3　不用 GT 的两个免费信号很值钱。**
在完全不用 GT 的组合里：

| 做法 | 段平滑 AP50 |
|---|---|
| 现有分数排序 + 不清理（复现 0a 的 0.362） | 0.362 |
| 现有分数排序 + 场景级 NMS + 丢掉只出现一帧的物体 | **0.721** |
| 排序换成"观测帧数"（记忆本来就统计）+ 不清理 | 0.647 |
| 排序换成"顶点数"+ 不清理 | 0.500 |

- "丢掉只出现过一帧的物体，再去掉重复"：0.362 → **0.721**。
- "只把排序分数换成被看到了几帧"：0.362 → **0.647**。
  两者都不需要训练，也不需要 GT。
出处：`work_dirs/stream_v2/phase0b/summary.md` §2。

**F0b.4　离上限的差距主要在排序，不在清理。**
0.877（上限）− 0.721（无 GT 最好）= 0.156。分解：
同样清理下把排序换成完美排序 +0.092；同样排序下把"挑不纯"换成 GT 版本只 +0.003。
说明**清理在无 GT 口径下已经基本做满，剩下的是排序**。
出处：同上。

**F0b.5　（上限）体素渲染天花板：观测点越稀越差。**
网格 GT 走 5 cm 体素再渲染回网格几乎无损（段平滑后 AP50 1.000，未平滑 0.999）；
同机制换成真实观测点（逐帧 20k 点、全帧累计）段平滑后 0.965（未平滑 0.941）。
即"观测覆盖完整时这条路能到 0.94 以上，观测越稀越差"。
出处：`work_dirs/stream_v2/phase0b/summary.md` §4。

**F0b.6　口径提醒：段平滑对小 mask 影响巨大。**
同一个组合在未平滑口径下要低 0.10-0.14（例：S_oracle+nms+all 平滑 0.877 / 未平滑 0.772；
S_conf+nms+single+all 平滑 0.721 / 未平滑 0.581）。引用数字时必须注明是否段平滑。
出处：同上。
